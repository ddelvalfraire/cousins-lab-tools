# Template V1 design review

Reviewed the current eight-file package in `/tmp/cousins-template-v1-design`, including the coordinator's tracker-handoff and ownership-diagram edits. This is one independent static review. No repository files were edited, and no runtime or scientific acceptance is claimed.

Verdict: request three focused contract corrections before D04 approval. The package can support user/team discussion now. Its production implementation gates remain closed.

1. **P2. Define how coalesced updates advance the stream checkpoint.** `contracts.md:141`, `contracts.md:153`, and `contracts.md:159-161` combine a monotonic change sequence, replay after a checkpoint, coalesced notifications, and unconditional resync for sequence gaps. If updates 41 and 42 become one notification carrying 42, a client at 40 sees the same gap as a missing message. Routine coalescing can therefore force repeated resynchronization. Preserve a separate contiguous delivery sequence, or include an explicitly covered checkpoint range in each coalesced message. State that coalescing cannot conceal an intervening analysis/control/lifecycle event. Add a D03 case that coalesces adjacent data notifications and interleaves one operation event without causing a false resync or skipping the event.

2. **P2. Separate analysis identity from the data snapshot used by an evaluation.** `contracts.md:27`, `contracts.md:89-90`, and `contracts.md:165-171` put durable watermarks into AnalysisContext, then allow the same context to extend to new watermarks. `read_interval` has no watermark argument, while `query_series` does. `architecture.md:123-127` similarly calls the input watermarks pinned. A session can create context A at row 100, display A through row 120 after an append, then ask for interval 110-120. The contract does not establish whether extraction is rejected, uses the original cutoff, or silently reads newer data. State whether every append creates a new context, or whether immutable analysis configuration and immutable evaluation input snapshots are separate objects. Under the latter approach, use an explicit evaluation snapshot or watermark set consistently for interval reads, measurement commits, series queries, and exports. Include an append-between-preview-and-commit acceptance case so the committed result uses identifiable inputs.

3. **P2. Complete the data bindings for the required XY charts.** `contracts.md:18-23` permits signal/calculation references but does not define a chart reference to calibration observation pairs or committed measurement fields. `architecture.md:69` likewise restricts charts to signal/calculation references. Yet `legacy-workflows.md:25-27` requires calibration XY charts and the M1 concentration/velocity plot, with duplicate concentrations preserved as distinct rows. A raw signal series and a collection of immutable result rows have different identities and iteration semantics. Add typed references for calibration observations and measurement fields, or explicitly define how the calculation model exposes those collections. Specify paired x/y values, stable row IDs, and treatment of retracted/superseded records. Add a C01 contract example with two measurements sharing one x value. This closes an existing V1 requirement without adding a component kind or graphical authoring.

The import proposal protects existing content with validation, immutable revisions, expected-head checks, idempotency, and explicit conflict handling. Exporting one revision while treating its parent as provenance is consistent with the stated file scope. Session snapshots and compatibility errors address the observed mutable-library lookup problem. Acquisition owns original records and physical effects, and operation acceptance remains distinct from physical success. Stop-generation handling and uncertain outcomes after crashes are explicit. I found no additional consequential contradiction in those areas.

In particular, scientific equations and tolerances, calibration-history policy, interval capabilities, legacy interchange, reset retention, representative recordings, and target hardware still need their named owners. D01-D04 correctly keep those decisions and approvals ahead of production work. Mockups are future work and are not represented as approved artifacts.
